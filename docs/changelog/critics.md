## ⚪ 缺陷 27：3500 词以上性能问题（暂时不影响但迟早要修） 「未修复 v1.0.1」

**优先级**：P3（当前 3500 词用户体感无卡顿；导入 2 万词时才会出现）
**排期建议**：v1.2 版本（用户量增长或支持导入外部大型词库后必须跟进）

### 27.1 查找全是 O(n) 「未修复 v1.0.1」

**涉及文件**：
- [WordBank.getWord() / hasWord() / updateWord() / addWord()](file:///g:/19725/code_part/project/NEWordRemberer/modules/WordBank.js)

#### 根因
当前所有查找函数都是 `this.words.findIndex(...)` / `some(...)` 线性遍历，即：
```js
hasWord(word) {
    return this.words.some(w => w.w.toLowerCase() === word.toLowerCase());
    // ↑ 3500 词查 1 次 = 3500 次字符串比较；导入合并 3500 词 = 3500² ≈ 1200 万次
}
```
3500 词时约 300ms 导入卡顿，2 万词时将达到秒级冻结。

#### 修复方向（v1.2 预研版）
构造 `this._index = new Map()` 索引（key = 小写单词，value = words 数组下标），O(1) 查找：
```js
// WordBank 构造函数：
this._index = new Map();
this.words = this.load();
this._rebuildIndex();   // 每次 save / import / init 后重建一次（3500 词 ≈ 0.1ms）

// 统一查找入口：
_findIndexByWord(wordStr) {
    if (!wordStr) return -1;
    return this._index.get(wordStr.toLowerCase()) ?? -1;
}
```
**额外收益**：顺便解决「大小写重复词条」的加载时去重合并（v1.0.1 没做这一层，QA04 只修了查找口径一致，没做旧数据合并清理）。

#### 改动后性能对比（预期）
- 3500 词 hasWord 查询 1 万次：修复前 ≈ 1200ms → 修复后 ≈ 1ms
- 导入合并 3500 词：修复前 ≈ 400ms → 修复后 ≈ 2ms

### 27.2 generateOptions 每次渲染都扫全词库 「未修复 v1.0.1」

**涉及文件**：
- [UIManager.generateOptions()](file:///g:/19725/code_part/project/NEWordRemberer/modules/UIManager.js)

#### 根因
每个英译中题目都要：
1. 遍历 3500 词 × 展开所有释义 → 约 5000~8000 个释义字符串
2. 排除正确释义 → 剩下的 sort 随机 → slice(0,5)
3. 下一题，**再做一遍**
背 125 题的话，这个循环跑 **125 × 3500 = 437500 次**，手机端 / 低配机「点下一题」卡顿 200~500ms。

#### 修复方向（v1.2 预研版）
UIManager 构造时**一次性**把所有释义建成扁平数组 `this._allDefinitionsPool`，之后只需从池子里随机 Fisher-Yates 洗牌 + Set 排除正确选项：
```js
// 构造时一次性建池（3500 词 ≈ 2ms）：
_rebuildDefinitionsPool() {
  this._allDefinitionsPool = [];
  this.wordBank.words.forEach(w => {
    try {
      const meanings = JSON.parse(w.m);
      meanings.forEach((m, idx) => {
        const key = `${w.w.toLowerCase()}__${idx}`;
        (m.c || []).forEach(def => this._allDefinitionsPool.push({ def: def.trim(), excludeKey: key }));
      });
    } catch (e) {}
  });
}

// generateOptions：从池子里取（每题 ≈ 0.08ms，不再卡）
generateOptions(word) {
  // ... Fisher-Yates 乱序 → 排除正确项 → 取 5 个干扰项 ...
}
```
addWord / importBackupData / clearReviewProgress 写完词库后，都要回调 `uiManager._rebuildDefinitionsPool()` 刷新池子。

#### 改动后性能对比（预期）
- 英译中 100 题生成干扰项：修复前 ≈ 400ms → 修复后 ≈ 8ms

## ⏳ 五、跨模块设计统一铁则（长期避免同类 Bug 根级规则，FINAL）

以下 6 条规则必须写入 Code Review 必查项（任何一条违反都不允许合入）：

1. **算法真相源唯一原则（缺陷 05 / 16 / 13）**：所有与 SRS 算法相关的计算必须**只在 MemoryCurve.js 里实现一份**；WordBank / TaskManager / UIManager 一律代理调用。
2. **校验入口 + 读时兜底双保险原则（漏洞 01 / 缺陷 17 / 18）**：数据入库前做 SchemaRegistry.validateWord 严格多层校验；数据读出使用时仍然用 try-catch 做降级处理，「上游已校验」永远不能作为「下游裸奔」的借口。
3. **用户数据主键统一原则（漏洞 04）**：任何单词查找 / 去重 / 更新 / 删除，必须统一使用 `w.w.toLowerCase()` 作为比较 key；禁止直接使用严格 `=== word.w` 匹配。
4. **UI 渲染零 innerHTML 原则（漏洞 02）**：任何来自词库、用户输入、备份导入的数据展示，一律使用 DOM API + textContent / createTextNode；Code Review 时必须 grep 整仓库所有 innerHTML，仅 Markdown 转义后静态 HTML 等明确场景才可放行。
5. **持久化失败必提示原则（漏洞 03）**：任何 save() / updateWord() 函数必须同时做三件事：① try-catch 所有异常；② 捕获异常立即通过 UI 明确提示用户（出了什么问题、下一步怎么做）；③ 提示后再向上抛出，禁止静默 return false。
6. **状态变量聚合原则（缺陷 08）**：任何一组「同弹窗或同流程」的状态变量必须打包成聚合 state 对象（如 importState / retryState），同时配套 DEFAULT_XX_STATE = Object.freeze({...})；打开流程时一次性用 DEFAULT 展开 reset，禁止散落成 N 个扁平成员变量手动逐个 reset。
